ERP AI Assistant Overview

Purpose: The ERP AI Assistant lets project managers ask business questions in plain English and receive SQL-backed answers from the verified ERP database.

Instead of exposing managers to table names, joins, or database tools, the assistant uses verified ERP knowledge to understand the question, select the correct business module, run safe read-only SQL, and present the result in a manager-friendly format.

Main Runtime Idea

  • The ERP schema is treated as stable, so verified business knowledge is reused instead of rediscovering everything at runtime.
  • Verified modules currently drive the strongest answers: Projects, Billing, Purchase Orders, Vendors, Store / Material Movement, Materials, and Inventory basics.
  • The assistant prefers approved relationships and deterministic SQL patterns before using fallback reasoning.
  • If a business meaning is unclear, the assistant asks a clarification instead of guessing.

Question Flow

How A Manager Question Works

Runtime Flow

  1. User asks a natural question. Example: “Compare billing of RDSS-VIZAG and RDSS-UGCABLE.”
  2. Semantic parser extracts intent. It identifies comparison, billing metric, project entities, date words, limits, and ordering.
  3. ERP binder maps business meaning. “Billing” is mapped to verified billing definitions, not guessed from similar table names.
  4. Entity resolver checks real data. Project, vendor, and material names are resolved against actual ERP values.
  5. Verified planner selects tables and joins. Only approved tables, columns, relationships, and aggregation grain are used.
  6. SQL is compiled and validated. The backend blocks writes, unsafe SQL, missing filters, wrong joins, and duplicate-risk totals.
  7. Read-only SQL runs on MySQL. Results are returned with row limits and timeout safety.
  8. Answer is rendered. The assistant gives a short summary, table, confidence, SQL details, and limitations when needed.

Clarification Flow

When the user question is answerable but missing key information, the assistant asks for the smallest useful clarification.

User: Compare purchase orders.

Assistant: Which two projects or vendors would you like to compare?

Options: RDSS-VIZAG and RDSS-UGCABLE, RDSS-VIZAG and RDSS-NELLORE, POLYCAB INDIA LIMITED and KEI Industries.

User: RDSS-VIZAG and RDSS-UGCABLE.

Assistant: Should I compare PO total value or PO count?

User: PO total value.

Result: The assistant continues the original question instead of treating the follow-up as a new query.

Why This Matters

Before

  • Follow-up answers could lose the original question.
  • Vague questions sometimes selected wrong tables.
  • Some questions failed with generic safe-query errors.
  • LLM could be asked to rediscover too much schema.

Now

  • Clarification state is stored per session.
  • Verified modules guide table, metric, and join selection.
  • Unsupported KPIs ask for definition instead of hallucinating.
  • Repeated successful answers can return quickly from Redis.

Answer Format

  • Short answer first: one clear business sentence.
  • Table when useful: rankings, comparisons, totals by project, vendor, material, or date.
  • Context: explains what the answer is based on, such as billing header value or PO total value.
  • Confidence: shows whether entity resolution, planning, SQL validation, and execution were reliable.
  • Limitations: shown only when important, for example when profit or low-stock thresholds are not verified.

Performance Approach

The application avoids sending the full 1,229-table schema to the LLM for normal verified questions. It uses verified catalog entries, compact context, Redis caching, read-only SQL execution, and live MySQL querying for large ERP data.

Known Limitations

  • Profit, margin, loss, performance, and risk require approved business formulas before the assistant should answer them.
  • Project details currently means verified project master information. A richer project profile can combine billing, PO, material movement, and inventory later.
  • Inventory low-stock logic needs a business-approved threshold or reorder-level rule.
  • Payroll, attendance, timesheets, BOQ, GRN, subcontract, and finance are not fully demo-certified yet.
  • Arbitrary database support is no longer the main goal. The POC is optimized for the stable ERP product schema.

Next Improvements

  • Expand the verified ERP catalog for remaining management modules.
  • Create a richer project summary combining billing, PO, material, and inventory facts.
  • Improve UI tables with sticky columns, better spacing, and polished clarification chips.
  • Freeze a benchmark set and measure answer accuracy after every catalog update.
  • Add more verified aliases for manager-style wording across the supported modules.

POC position: The assistant is demo-ready for verified ERP management questions across Projects, Billing, Purchase Orders, Vendors, Store / Material Movement, and basic Inventory. It should clarify ambiguous questions and avoid inventing unsupported KPIs.
